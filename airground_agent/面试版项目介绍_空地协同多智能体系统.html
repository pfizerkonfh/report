0. 30 秒电梯演讲（开场直接背）

我做的是国网变电站「空地协同」无人巡检系统里的决策大脑——第 4 子项，多智能体任务分配与边缘智能决策。 简单说就是把运维人员的一句话，比如"去查一下高空绝缘子和地面开关柜"，自动变成一份可执行作业计划： 哪些活派给无人机、哪些派给机器狗，每一步在哪算（端侧、边缘还是云端）， 前后依赖怎么排，中途失败了怎么恢复。

技术上是用 Python + LangGraph 搭的两层 Agent：上层 Planner 做目标分解出 DAG， 下层 Reasoner 走 ReAct 逐步执行，中间用可判定的 Precondition / Effect 语义契约把"大模型乱调工具"从提示词约束变成机制约束； 执行侧我抽了一层 ToolAdapter，把语义契约和物理执行通道解耦，现在有离线 Mock、硬件在环仿真、录播回放、ROS2 真机四种通道， 换真机只换 Adapter，决策层零改动。

这一轮我还接了自己做的 3DGS 场景重建产物，让占据栅格查询和 A* 路径规划变成真实计算而不是假数据。 目前 65 个测试全通过，真实大模型跑通端到端，动作合理度 1.0、前置校验零违例。 但要说清楚：现在还没有真机实测数据，电量里程都是行为模型推演，它是个方法正确、接口正确的原型，不是交付产品。

2. 背景：到底在解决什么

2.1 业务侧

变电站巡检目前高度依赖人工，高空设备要爬、要停电配合，效率低且有安全风险。已有的无人巡检方案多是"单一平台 + 固定航线"——无人机飞一遍、机器人走一圈， 两条线各干各的，任务分配靠人预先编排。"空地协同"的难点不在单个平台能不能飞、能不能走，而在于一句话需求进来后，谁去干、按什么顺序干、干到一半出问题怎么办。

2.2 技术侧：六个必须回答的问题

#问题为什么难 / 我的切入点
①长程任务分解与可恢复一次巡检是十几步的长链条，中途某步失败后不能从头再来，也不能盲目重试。→ 分层 Agent + 重规划 + Reflexion 归因
②工具误调用大模型最容易出的错：没素材就去剪辑、随便换个工具绕过报错。光靠提示词约束不住。→ Precondition/Effect 语义契约做机制级阻断
③边缘时延端侧算力有限，云侧往返太慢。→ 端-边-云三层路由 + 端侧 VLA 优先、云端兜底
④效果无法量化"这个 Agent 好不好"说不清。→ 统一评测体系 + 失败归因（区分是规划错还是执行错）
⑤平台维度缺失通用 Agent 框架没有"无人机 / 机器狗"这种物理平台概念。→ 新增 Platform 维度，与计算层级正交建模
⑥从原型到真机的鸿沟工具全是 Mock，接真机就要重写决策层。→ ToolAdapter 抽象层 + 硬件在环仿真提前暴露真机问题

这是本项目最容易被误解、也最值得在面试里讲清的一点。"无人机 / 机器狗"是物理平台，"端侧 / 边缘 / 云端"是计算层级，两者完全独立：

图 2：平台 × 层级 正交分配矩阵。每个子任务先判物理平台（谁去干），再判计算层级（在哪算）。

为什么要正交？因为"无人机"和"边缘"不是一件事——无人机的视觉避障要跑在机载端侧（时延敏感），但它拍回来的缺陷识别可以上云（算力密集）； 机器狗的栅格路径规划可以在边缘站算，但越障必须板载实时响应。要是把两者揉成一个标签，这个矩阵里大半格子就表达不出来了。

4. 我的职责（简历里的"个人职责"展开版）

  1. 方案设计：把"空地协同"拆成可建模的两个正交维度（物理平台 / 计算层级），设计规划-推理-路由-执行四层架构与它们之间的接口契约。
  2. 规划层实现：基于 LangGraph 状态图实现 decompose → validate ⇄ retry 的分解校验闭环，输出带成功判据的 DAG，校验项包括无环性、工具可达性、依赖闭合。
  3. 推理层实现：ReAct 循环 + 目标对齐拦截 + Precondition 阻断升级 + Reflexion 失败归因与经验回流（ExperienceBuffer → 注入下一次规划）。
  4. 工具语义层：为每个工具定义 Precondition / Effect / Rollback / RouteHint 的语义契约，使"能不能调"变成可判定的布尔表达式而非提示词。
  5. 执行通道抽象：设计 ToolAdapter，把语义契约与执行通道解耦，实现 legacy / sim / playback / ros2 四种通道，含真机四要素（真实耗时、超时、取消、遥测）。
  6. 感知层接入：把 3DGS 重建产物接入决策链路，实现占据栅格、连通性、A* 规划与高度剖面，并修复"仿真通道吞掉真实计算结果"的语义缺陷。
  7. 评测与可观测：搭建统一评测体系与失败归因；实现 SSE 流式前端（DAG、ReAct 轨迹、平台着色、实时遥测、急停）。

5. 核心技术点（每个都能展开讲 3 分钟）

5.1 用"可判定契约"替代"提示词约束"，根治工具误调用

问题：大模型 Agent 最典型的失败是幻觉调用——没有素材就直接调剪辑、被拒绝后擅自换个工具绕过。
方案：每个工具声明 preconditions（前置事实）、effects（产出事实）、rollback、route_hint。 执行前对前置条件做布尔求值，不满足就阻断并升级重规划，不允许模型自己换工具——因为"换工具"这个决策权一旦交给模型，契约就形同虚设。
结果：实测真实大模型端到端跑测中前置校验违例 0 次，动作合理度 1.00。

面试加分点：这套设计和经典规划里的 PDDL / STRIPS 是一脉相承的——动作由前置与效果描述，只是这里的前置条件求值对象是一个动态世界状态字典，且前置不满足时的处理策略是"升级给规划器"而不是"交给模型临场发挥"。

5.2 长程任务的恢复机制：重规划 与 Reflexion 的分工

问题：十几步的作业链，某步失败后从头再来太贵，原地重试又可能死循环。
方案：分两级恢复。轻症：前置不满足 → 最多 2 次重规划（把 Reflexion 沉淀的 lessons 注入 Planner 上下文，让重规划"带着教训"重来）； 重症：重规划仍失败 → 触发 Reflexion，回放轨迹、推断失败层（PLANNING 还是 ACTION）、生成 critique 与 lesson 写入 ExperienceBuffer，供同类目标的下次规划复用。
结果：失败不再表现为"卡死"或"乱调一通"，而是有归因的结构化结论；实测真实跑测 6 步全程 0 次重规划、0 次反思（成功率侧），而注入故障的仿真用例能稳定触发并归因。

失败层推断怎么做的：从错误信息里正则提取被判定的事实键（如 safety_cleared），再遍历工具集看是否存在能产出该事实的工具——有则说明是执行层没安排好（ACTION），没有则说明计划本身不可行（PLANNING）。这个判断决定了下次是该"补一步"还是"换条路"。

5.3 ToolAdapter：让"接真机"从重写变成替换

问题：原型阶段工具全是 Mock，返回值是 uuid 假路径、耗时为零。真要接无人机，如果执行细节散落在决策层，就得大改。
方案：把「语义契约」（ToolSpec：前置/效果/回滚/路由提示）与「执行通道」（ToolAdapter）彻底分开。Adapter 必须实现真机四要素： ① 真实墙钟耗时（可用 time_scale 加速仿真）② 真实超时预算 ③ 可取消（CancellationToken，约 50ms 响应）④ 遥测回传（电量/里程/位置/链路/相位）。
结果：四种通道并存（legacy / sim / playback / ros2），换真机只换 Adapter，Planner、Reasoner、Router、评测层零改动。

5.4 硬件在环仿真：把真机问题提前到没有真机的时候

问题：Mock 模式下一切顺利，一接真机就会暴露一堆问题——超时、状态不同步、停不下来。
方案：仿真 Adapter 按平台建模真实作业相位（无人机：自检→起飞→巡航→航拍→返航→降落；机器狗：上电→导航→近距细查）， 真实墙钟 sleep、电量按飞行消耗、位置推进，并可注入作业失败、链路中断、低电拒飞、超时等故障。
结果：实测这一层暴露了 7 个在 Mock 模式下永远发现不了的真实缺陷，包括： 默认 30s 超时预算不够一个无人机架次（改 120s）、适配器忽略上下文超时预算、只回传电量不回传语义 Effect 导致后续步骤全线阻断、 急停后仍继续重规划与反思（安全事故）——修复后急停响应从约 95s 降到 6.7s。

5.5 真实感知层：把 3DGS 重建产物接进决策链路

问题：系统的感知是空的——camera 返回一个假路径，footage 只是个字符串标记。整个决策链跑在纯逻辑仿真上。
方案：接入自采实验室场景的 3DGS 重建产物：占据栅格 nav_data.json、降采样点云 nav_points.json、重建质量 metrics.json。 严格沿用原管线的坐标系约定（X-Z 水平、Y 竖直、occ[ix][iz]、wx = xmin + (ix+0.5)·res）， 实现坐标转换、最近可通行点纠偏、8 连通洪泛连通性、8 邻域 A*（禁穿墙角）、点云高度剖面，并封装成 4 个真实工具。
结果：实测栅格 53×125 @0.2m（10.6×25.0m）；可通行 559 / 障碍 2978 / 未知 3088 格，已知率 53.4%； 重建 PSNR(test) 28.06 dB、高斯 387299、位姿 98。 A* 规划得 58 格 / 11.73m，与原管线导出的参考路径 58 步完全一致——跨管线一致性得到验证。 真实大模型已能自主把 map_query / route_plan 编入计划并真正调用。

5.6 一个只有"真跑起来"才会暴露的语义缺陷

现象：真实跑测里 Planner 明明调了 route_plan，最终世界状态却是 route_ready=False、route_len_m=0.0，观测文本是模板化的"route_plan 完成"。
根因：仿真通道只调 Adapter、从不调工具的 run()，而感知工具的真实计算写在 run() 里；Adapter 用工具静态声明的默认 Effect回写，等于把真实 A* 结果覆盖掉了。
修复：给 ToolSpec 引入 compute_only 语义——纯计算/查询类工具没有物理动作，其观测与副作用必须来自真实计算；执行器新增通道：先跑通道取时序与遥测（传空 effects 禁止静态回写），再跑真实 run() 覆盖。
结论价值：这个缺陷不在算法逻辑里，而在模块边界上（纯计算工具与物理执行工具的语义差异）。这类问题只有把系统真跑起来才会出现。

5.7 可观测性：SSE 流式前端

纯标准库实现 ThreadingHTTPServer + Server-Sent Events，把规划、选择、推理、执行、进度、反思、评测全部事件化。 前端实时展示 DAG（SVG 分层）、ReAct 轨迹、按平台着色的节点、真实遥测（电量/里程/相位百分比）、评测指标，运行中可随时中止（走 CancellationToken）。 长任务的相位进度做了每 10% 节流，避免事件风暴。

7. 面试高频问答（按被问概率排序）

Q1：这算"多智能体"吗？看起来像单个大模型在跑流程。

这是个好问题，我会如实分层回答。系统里有两类"多智能体"含义：

一是角色分工的智能体：Planner（只分解不碰参数）、Reasoner（只执行不改写计划）、Router（只选路）、Executor（只管通道）、Evaluator（只评测）， 每个角色有明确的输入契约和权限边界，比如 Planner 不允许编造工具参数、Reasoner 不允许自造计划。这是职责隔离意义上的多智能体。

二是物理平台的异构体协同：无人机和机器狗是两套运动学、两套传感器、两套作业约束，系统要把同一目标分配给不同物理体，这本身是异构多智能体协同问题。

必须承认的限制：当前 Reasoner 是串行执行（取就绪节点第一个），没有真正利用两个平台可以并行的物理条件。这是我明确的下一步（阶段 C）， 需要引入并发调度 + 共享世界状态的写冲突处理（不同平台写不同事实域，冲突主要在共享资源如充电位、作业空域）。

Q2：怎么保证大模型不乱调工具？提示词里写"不要乱调"不行吗？

不行，这是我特意做了机制设计的地方。提示词约束是软约束，模型在上下文变长、任务变复杂时会退化。我改成了可判定的硬约束：

每个工具声明 preconditions（如 safety_cleared == True、footage != None），执行前对当前世界状态求值，不满足直接阻断， 并把错误升级给 Planner 重规划，而不是让模型临场换工具——因为一旦允许模型自己换，契约就被绕过了。

效果：真实大模型跑测中前置违例 0 次、动作合理度 1.00。另外还有一层目标对齐校验：模型给出的 action 必须绑定到当前计划内仍待完成的子任务，否则拦截。

Q3：为什么用 LangGraph 而不是自己写 while 循环？

三个实际理由：

① 控制流显式化。我的 Planner 不是一次调用，而是 decompose → validate → 失败回退 retry 的带环流程； Reasoner 是 select→reason→execute→post→(continue / replan / reflect / cancelled) 的多分支路由。用图描述比嵌套 if/while 清晰得多，也更好改。

② 状态与重状态分离。Plan、WorldState、GoalRegistry 这些大模型对象不进图状态（避免序列化问题），挂在实例上共享，图里只跑轻量控制状态（step、status、errors、trace）。

③ 可测试与可观测。每个节点是纯函数式的 Dict 输入输出，好单测；条件边天然对应可 emit 的事件，前端能实时看到"现在在哪个节点"。

当然代价是引入了框架依赖和一定学习成本——如果只是一个线性 pipeline，我不会上 LangGraph。

Q4：无人机和机器狗怎么分配的？是规则还是模型？

模型优先，规则兜底，两条腿。

Planner 提示词里明确定义了三值平台语义（uav = 高空视野/航拍/大范围；dog = 地面近距/表计/狭窄区域；shared = 纯计算任务）， 并强调"凡涉及实地采集的子任务必须显式判给 uav 或 dog，不要一律用 shared"。真实跑测里模型确实判对了：航拍绝缘子 → uav，查开关柜 → dog。

兜底函数 _resolve_platform() 按优先级：显式 platform → 从 id/描述关键词推断（中英文兼容）→ 工具的 platform_hint → shared。 这样即使模型漏标，也不会退化成"全是 shared"。

被追问"为什么不直接用规则"：因为规则能覆盖的只是关键词命中，像"看一下那个发热的接头"这种歧义句需要语义判断；而纯模型的风险是漏标和幻觉，所以要兜底。

Q5：上真机了吗？有没有实测数据？

没有，这点我不含糊。目前系统除软件响应外，没有任何一条真实机器人硬件实测数据。

电量、里程是仿真行为模型推演的；端侧 VLA 时延是公式估算的；安全联锁（safety_cleared）目前是内置默认值——真机部署时必须改由真实安全联锁与机载遥测写入，我在代码注释里也标注了。

所以它的价值在方法设计与工程实现，不在真机性能论证。我做的硬件在环仿真，作用就是在还没有真机的时候把真机会暴露的问题先暴露出来——它确实做到了，暴露了 7 个缺陷。

Q6：项目里最难的是什么？

不是算法，是语义边界的界定。举个具体例子：开发一个工具时你要回答"它到底有没有物理动作"。

一开始我没区分，结果仿真通道把所有工具一视同仁地"跑一遍通道、套用静态声明的效果"， 导致 route_plan 的真实 A* 结果被默认值 route_len_m=0.0 覆盖掉——模型以为规划成功了，其实什么都没算。

修法是引入 compute_only 语义：纯计算工具没有物理动作，它的观测和副作用必须来自真实计算，通道只贡献时序和遥测。 这类问题的共同特点是：不在任何单个模块的代码逻辑里，而在模块之间的边界上，只有把系统真跑起来、看真实数据，才会浮现。

Q7：遇到最严重的一个 bug 是什么？

急停后系统仍在自主行动。用户点中止，CancellationToken 已置位，但 Reasoner 把"取消导致的执行失败"当成普通可重试失败， 继续走 replan → 再选下一步 → 甚至触发 Reflexion，从取消到真正停机要 95 秒。

这在真机场景是安全事故——操作员按下急停，无人机还在按自己的计划飞。

修法是把"取消"提升为独立的终止语义：在 select 节点最前面检查令牌，已取消就直接 emit cancelled 并终止； execute 后也判定，取消不走 replan/reflect 分支。修复后停机时间 6.7 秒。

这个 bug 只在硬件在环仿真里才出现——Mock 模式零耗时，根本看不出来。

Q8：和你的 3DGS 研究怎么结合的？

这是我做这个项目时一个很自然的交叉点。我发现系统最大的空洞是感知层——地图是假的、路径是假的，整个决策链跑在纯逻辑上。

而我本身在做 3DGS 场景重建和占据栅格地图，产物正好可以直接填这个洞：把 nav_data.json 的占据栅格接进来， map_query 查某点是否可通行、route_plan 在真实栅格上跑真实 A*，返回真实里程； height_probe 用点云算高度剖面（无人机看净空够不够、机器狗看地面是否平整）。

关键是坐标系不能自造：我严格沿用了原管线的约定（X-Z 水平、Y 竖直、occ[ix][iz]）， 所以我在真实栅格上重跑的 A* 得到 58 格，与原管线导出的参考路径 58 步完全一致——这条一致性校验是我认为最有说服力的一点。

更进一步的结合：重建质量指标（PSNR、已知率）可以变成可判定的前置条件，比如"已知率低于阈值时先补扫再作业"， 这让感知质量第一次能参与决策，而不只是个展示数字。

Q9：端-边-云是怎么选路的？VLA 是什么？

每个工具带 route_hint（倾向端/边/云），Router 结合 NetworkGovernor 给出的链路状态（RTT、带宽、边侧是否可用）决策， 策略是端侧优先、云端兜底：时延敏感且边侧能做的下沉，算力密集或边侧不可用时上云。

VLA 是 Vision-Language-Action 模型，这里指跑在端侧的 3B 规模、INT4 量化的小模型，负责视觉条件下的即时动作（避障、越障、局部导航）， 设计目标是低时延（目标 ≤65ms）。必须说明：这里的 VLA 是时延模型仿真，不是真的部署了模型——真实部署是我路线里的阶段 C/D。

Q10：怎么评测一个 Agent 系统？指标怎么来的？

我建了统一评测体系，分四类：① 结果类：规划成功率、成功判据是否达成；② 过程类：动作合理度、前置校验违例数、重规划次数； ③ 性能类：单步 p50/p95/p99、端到端耗时；④ 体验类：CSAT（外部传入）。

我认为更重要的是失败归因：失败时要能定位到是 PLANNING 层（计划本身不可行）还是 ACTION 层（执行没安排好）。 判断方法是看被阻断的那个事实键，有没有工具能产出它——有就是 ACTION，没有就是 PLANNING。 没有归因的评测只会告诉你"失败了"，有了归因才能驱动 Reflexion 生成有效的 lesson。

Q11：如果重做一次，你会改什么？

三件事：

① 一开始就做执行通道抽象。我是先写 Mock、后抽 Adapter 的，中途返工。如果重来，第一天就定义 ToolSpec 与 ToolAdapter 边界。

② 尽早接真实数据。感知层是最后才接的，接上之后立刻暴露了两个真问题（计算结果被覆盖、Web 默认路径初始化缺失）。 真实数据的价值不只是"更真实"，而是让隐藏的边界缺陷显形。

③ 并发调度一开始就要进设计。现在 Reasoner 串行，改成并行要动世界状态写入、资源竞争、事件合并，属于结构性改动而不是补丁。

Q12：这个系统现在能上真实业务吗？

不能，我会直接说不能。分七层看：软件正确性与架构可扩展性已就绪；感知数据基础部分就绪（有真实重建产物但只有单一静态场景）； 执行能力（全通道未接真机）、端侧推理（模型仿真）、安全联锁（内置默认值）、工程化（无持久化/鉴权/多用户/审计）均未就绪。

落地路径我排的是：A 硬件在环仿真（已完成）→ B 接单台真机（先机器狗，约束更少）→ C 空地并行协同 + 真实端侧 VLA → D 现场闭环与长期稳定性。
