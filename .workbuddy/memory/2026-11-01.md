## 新增：本地虚拟狗联调台（dog/devkit/）
- 目的：在没有真机的开发机上，用"虚拟狗"把整条下发链路跑通（真实 WS 连接 + 真实子进程 stdin/stdout，零硬件风险），验证通过后接真狗只需改 IP。
- 文件：`virtual_dog_ws.py`（`VirtualDogWsServer`，模仿 alg_control_node 的 app_req/app_resp 帧协议 + StandBy/Navigating 状态机）、
  `virtual_zsibot_control.py` + `fake_zsibot_control.{bat,sh}`（模仿 zsibot_control --daemon，响应对齐 main_sdk.cpp 的 send_json_response）、
  `sample_mission.py`、`run_virtual.py`（一键联调 CLI）、`__init__.py`。
- 测试：`tests/test_dog_virtual.py` 3 项（runner 全链路 / 适配器直调 route_plan / 急停），全过；全量测试现 101 项通过。
- 踩坑：websockets 16.x 的 `serve()` 必须在已运行的事件循环内 await，否则 Server.__init__ 调 get_running_loop() 抛 "no running event loop"；
  虚拟狗关停改用 `asyncio.Event` 信号 + `server.close()/wait_closed()`，避免 loop.stop() 导致的 "Event loop is closed" 告警。
- 关键约束（接真机）：`zsibot_control` 是 Ubuntu 上 make 的 C++ 二进制，`SdkDaemonClient` 当本地子进程拉起，故**动作通道必须在装 SDK 的 Ubuntu 上跑**；
  导航 WS 可任意联网机器。最干净是把整个 airground_agent 跑在狗所在 Ubuntu 网关。坐标标定（fit_from_point_pairs）是安全红线，未标定不可导航。
- README §⑤.1/⑤.2 已记录联调台用法与接真机分级试车步骤。
